# Visual Learning Standard — All 40 Lessons

## Purpose

Use visuals to make beginner web-development concepts easier to understand. Every visual must teach, clarify, or guide an action. Do not add pictures only for decoration.

## Visual types

1. **Concept diagrams:** original diagrams for ideas and processes, such as browser requests, the CSS box model, or JavaScript events.
2. **Interface screenshots:** real screenshots from the software students use, such as Visual Studio Code, Chrome DevTools, GitHub, and GitHub Pages.
3. **Code illustrations:** small, readable code examples with labels or callouts. Keep the actual code as selectable text in the lesson as well.
4. **Wireframes and previews:** simple page layouts and project previews that show the expected result before students build it.
5. **Practice visuals:** annotated screenshots or diagrams that support a practical task.

## Placement by material

| Material | Visual approach |
|---|---|
| Lecture notes | Place 2–4 useful visuals near the concepts they explain. Use fewer when a topic is simple. |
| Instructor guide | Include demonstration screenshots, diagram references, and notes about what to point out. |
| Practical exercises | Use step screenshots for software tasks and diagrams for layout or process tasks. |
| Homework | Include an example or small visual only when it makes the expected result clearer. |
| Daily quiz | Use a visual question only when identifying or interpreting an image is part of the learning outcome. |
| Project instructions | Include a wireframe or sample preview so students understand the target. |

## Image quality rules

- Use simple English labels and captions.
- Keep text large enough to read on a classroom projector.
- Use a consistent, calm visual style and clear contrast.
- Prefer original SVG diagrams for concepts; they remain sharp when enlarged.
- Use genuine screenshots for software interfaces. Do not create fake screenshots that look like real software.
- For screenshots, use the current version of the tool where possible. Add arrows or numbered callouts only when they improve clarity.
- Keep screenshots cropped to the relevant area. Hide personal information, account details, tokens, and private data.
- Use images that the academy has permission to use. Prefer original diagrams, academy-created screenshots, and properly licensed assets.
- Add useful alternative text and a short caption to each instructional image.
- Store lesson images in that lesson's `images/` folder.
- Use descriptive, lowercase, hyphenated filenames, for example `css-box-model.svg`.
- Link to the original image file in the lesson repository so students can open it at full size.

## Accessibility and student use

- Never communicate an essential instruction only through colour.
- Explain the same important idea in nearby text.
- Use readable labels and meaningful alternative text.
- Avoid crowded diagrams and screenshots with tiny text.
- Do not assume every student can distinguish colours easily.

## Suggested visual quantity

Aim for 2–4 meaningful visuals in lecture notes for a typical lesson. A lesson may need more screenshots when it teaches a software workflow, or fewer when a topic is straightforward. Relevance is more important than a fixed number.

## Review checklist

Before publishing a lesson, check:

- [ ] Every image supports a stated learning outcome.
- [ ] The image appears beside the explanation or step it supports.
- [ ] Labels and captions use simple English.
- [ ] The visual is readable on a classroom screen.
- [ ] Alternative text describes its purpose.
- [ ] Screenshots show the correct software and a safe example.
- [ ] The lesson still makes sense if an image does not load.
- [ ] Any external asset has a suitable licence or permission.

## Implementation rule

Apply this standard to all 40 sessions. Build and review visuals lesson by lesson so that screenshots match the actual software workflow and diagrams match the exact content taught. Do not publish placeholder screenshots or misleading interface images.
